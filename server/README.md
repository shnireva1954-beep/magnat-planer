# Свой сервер Магната

С 02.10.2026 сайт переезжает с GitHub Pages на свой сервер в России
(RUVDS, Королёв, `193.108.113.70`, Ubuntu 24.04, 1 ядро / 0,5 ГБ).
Решение владельца — «как профессиональнее, так и делай, мне нужен премиум
продукт».

**Зачем.** Оплата на сайте и вход по почте требуют своего сервера, а 152-ФЗ
велит хранить данные россиян в России. Репозиторий можно закрыть — код и
история перестанут быть видны всем. Свои заголовки безопасности (CSP, HSTS),
и сайт ближе к клиенту.

## Как устроено

```
GitHub main ──(раз в минуту, ключ только на чтение)──► /var/lib/magnat/src
                                                          │ git archive, без служебного
                                                          ▼
                                     /srv/magnat/releases/<коммит>   (пять последних)
                                     /srv/magnat/current ──► одна из них (атомарно)
                                                          ▲
                              Caddy: HTTPS сам, заголовки — server/Caddyfile
```

| Что | Где |
|---|---|
| Выкладка и состояние | `/usr/local/sbin/magnat` ← `server/magnat.sh` |
| Таймер выкладки | `magnat-deploy.timer` (раз в минуту) |
| Настройки веб-сервера | `/etc/caddy/Caddyfile` ← `server/Caddyfile`, сам сверяется с `main` |
| Ключ к GitHub | `/var/lib/magnat/deploy_key` (только чтение, только этот репозиторий) |
| Установка | `server/install.sh`, повторный запуск безопасен |
| API входа по почте | `/srv/magnat-api/current` ← `server/api/` (служба `magnat-api`, только `127.0.0.1:8787`) |
| База API и её копии | `/var/lib/magnat-api` (только пользователь `magnat-api`), копии — `backup/`, семь последних |
| Почта для кодов | `/etc/magnat/smtp.env` (только root), заполняет `magnat mail` |
| Ключи Платеги (оплата Магната) | `/etc/magnat/platega.env` (только root), заполняет `magnat platega` |

- **Служебное не выкладывается дважды:** выкладка вырезает список `exclude`
  из `_config.yml` (плюс `server/`, `CNAME`, файлы на «.» и «_»), а Caddy всё
  равно отвечает на них 404.
- **Битый коммит не выкладывается:** нет `index.html` Магната — остаётся
  прежняя версия.
- **Сломанный `Caddyfile` не применяется:** сначала `caddy validate`, после
  применения сайт обязан ответить, иначе возвращается прежний.
- **Сертификат — сам**, Let's Encrypt через Caddy. Пока адрес смотрит на
  GitHub, получить его нельзя; как только DNS повёл сюда, выкладка в течение
  минуты перезапускает Caddy за сертификатом (иначе Caddy ждал бы до часа).
- **Журнала посетителей нет:** адрес посетителя — персональные данные, а
  пользы от журнала нам нет.
- **Защита:** ufw (открыты только SSH, 80, 443), fail2ban на SSH,
  автообновления безопасности и Caddy, подкачка 1 ГБ на случай нехватки памяти.

Команды на сервере (каждая — одна строка в Termius):

| Команда | Что делает |
|---|---|
| `magnat status` | что сейчас на сервере — это и присылать в чат |
| `magnat rollback` | вернуть прошлую версию сайта; API вернётся вслед за ним в течение минуты |
| `magnat mail` | почта для кодов входа: спросит ящик и пароль, пошлёт проверочное письмо |
| `magnat restart` | перезапустить API и Caddy и снова попробовать новый API, если он не встал |
| `magnat upgrade` | переустановить сервер из той версии, что сейчас на сайте (когда `status` просит) |

Проверка всего этого — `tests/06-server.js`, входит в `tests/run.js`.

## Вход по почте: API на этом же сервере (11.10.2026)

Для входа в Магнат по коду из письма на сервере появилась вторая программа —
API (`server/api/api.py`). **Пока он закрыт:** код получают только два ящика
владельца из настроек почты, для посетителей сайта ничего не меняется.
Открывается он отдельным решением, после текстов и уведомления в Роскомнадзор.

**Как устроено.** API слушает только саму машину (`127.0.0.1:8787`); снаружи
к нему ведёт один путь — `https://magnat-planer.ru/api/…` через Caddy, с теми
же заголовками безопасности, без журнала посещений. Caddy сначала сам
дочитывает запрос целиком (до 2 МБ) — медленный клиент держит его, а не API;
API выключен — Caddy отвечает `{"ok":false,"err":"down"}`, а не страницей.
API работает от своего пользователя `magnat-api` в песочнице: писать может
только в `/var/lib/magnat-api`, памяти — не больше 96 МБ (у машины 366 МБ).
Код из репозитория root не запускает никогда.

**Обновляется сам, вместе с сайтом.** Новый коммит в `main` с другим
`server/api` — выкладка сначала гоняет новый API на копии базы, потом
делает копию самой базы (`/var/backups/magnat/deploy`), переключает и ждёт
ответа именно новой версии. Не прошёл проверку или не ответил — работает
прежний, а этот выпуск больше не пробуется (до следующего изменения API).
Сайт выкладывается в любом случае. Сам скрипт сервера себя не обновляет —
`magnat status` скажет «скрипт сервера устарел», тогда `magnat upgrade`.

**Копия базы** — раз в сутки (около 03:40 по Москве), на этой же машине,
семь последних; сразу после удачной копии — обслуживание базы (`api.py
maintain`: старые коды и сессии, аккаунты без входа два года, неоплаченные
заказы — 30 дней, заказы — 5 лет; строка «обслуживание базы: …» в журнале
`magnat-api-backup`). Следом (около 04:10) `magnat backup` от root: если настроено
(раздел «Копия вне сервера» ниже) — зашифрованная копия на Яндекс Диск
владельца; письма-напоминания на адрес поддержки (копия не ушла две ночи
подряд, места меньше 2 ГБ, оплата сервера через 5 дней); чистка копий старше
30 дней.

### Что сделать один раз — по шагам

1. **Termius → сервер → та же строка установки** (повторный запуск
   безопасен; нужна именно она, а не `magnat upgrade`, — старый скрипт на
   сервере этой команды ещё не знает):
   ```
   command -v git >/dev/null || (apt-get update -qq && apt-get install -y -qq git); rm -rf /root/magnat-setup && git clone -q --depth 1 https://github.com/shnireva1954-beep/magnat-planer /root/magnat-setup && bash /root/magnat-setup/server/install.sh
   ```
   Появится шаг `--- 5/8 API входа по почте ---` и строка
   `[ОК] API входа работает (закрыт: код получают только ящики владельца).`
   В конце — `VSE-GOTOVO`.
2. **Ящик для кодов — на Mail.ru**, отдельный, только под Магнат. Яндекс не
   подойдёт: с этого сервера почта Яндекса недоступна (проверено 11.10).
3. **Пароль для внешнего приложения** (не обычный пароль от ящика!):
   Mail.ru → «Настройки» → «Безопасность» → «Пароли для внешних
   приложений» → «Добавить». Имя — например «Сервер Магната». Если спросят,
   для чего пароль, — выбери отправку писем (SMTP). Mail.ru покажет пароль
   один раз — **набирай его только на сервере, в чат не присылай.**
4. **Termius → сервер:**
   ```
   magnat mail
   ```
   Спросит три вещи: адрес ящика для кодов, пароль приложения (букв на
   экране не видно — так и надо) и адрес поддержки — на него придёт
   проверочное письмо «Проверка: почта Магната настроена». Сервер почты
   для Mail.ru подставится сам (`smtp.mail.ru:465`). Успех выглядит так:
   ```
   Проверяю: шлю письмо на <адрес поддержки> через smtp.mail.ru:465…
   ПОЧТА РАБОТАЕТ — проверочное письмо ушло на <адрес поддержки>. Коды входа будут приходить с <ящик для кодов>.
   ```
5. **`magnat status`** — прислать вывод в чат. Новые строки:
   ```
   API входа:      работает ✅ версия 3f2a1c9e0b1d, вход закрыт (код — только ящикам владельца)
   Почта для кодов: настроена — <ящик для кодов> ✅
   Копия базы:     ещё не было (делается сама раз в сутки)
   Яндекс Диск:    копии не настроены (по желанию, один раз: magnat backup-setup)
   Место на диске: свободно 7,2 ГБ
   Оплата сервера: срок не записан → magnat paid-until ДД.ММ.ГГГГ
   ```
   Пароля в выводе нет и не будет — он лежит только в `/etc/magnat/smtp.env`
   (читает только root).

### Если сломалось

- **`НЕ УШЛО: ящик не пустил…`** — пароль приложения неверный (часто — ввели
  обычный пароль от ящика) или в настройках почты Mail.ru не разрешены
  почтовые программы. Создать новый пароль приложения и снова `magnat mail`.
- **`НЕ УШЛО: сервер не достучался до …`** — сеть; прислать вывод в чат.
- **`НЕ УШЛО: ящик отказался отправить письмо…`** — проверить адрес
  поддержки; не помогло — прислать вывод.
- После любого «НЕ УШЛО» прежние настройки почты не тронуты — сайт и вход
  работают как работали.
- **`API входа: не отвечает ❌`** — `magnat restart`, через минуту
  `magnat status`. Не помогло — прислать вывод `magnat status` и
  `journalctl -u magnat-api -n 30`.
- **`⚠ Скрипт сервера устарел — набери magnat upgrade`** — набрать
  `magnat upgrade`: переустановка из той версии, что сейчас на сайте (не из
  сети), в конце — `VSE-GOTOVO`.
- **`Копия базы: … ⚠ старше суток — не делается`** — служба копии не
  отработала; `magnat backup` сделает сейчас, не вышло — прислать вывод и
  `journalctl -u magnat-api-backup -n 20`.

### Копия вне сервера — Яндекс Диск (по желанию, один раз)

⚠️ Слоты на Диске перезаписываются по кругу (14 по дню года), а не по возрасту:
если сервер умер или выгрузка долго не шла, старые копии лежат на Диске, пока
не стереть руками папку приложения — политика обещает не дольше 30 дней.

Машину RUVDS могут снести вместе с копиями; данные людей останутся в их
телефонах, но аккаунты и история версий живут только здесь. Поэтому копия
базы каждую ночь уходит ещё и на Яндекс Диск владельца: в папку приложения
(токен видит только её), зашифрованная фразой-ключом — Диск хранит
шифртекст, без фразы копию не открыть никому. На Диске 14 слотов по дню
года — не больше двух недель истории, как обещано в политике. WebDAV Диска
Яндекс закрывает (осень 2025, не работает и у платных) — поэтому официальный
REST API: адрес загрузки → PUT → сверка размера и md5 с отправленным.

1. **Токен.** На телефоне или компьютере, войдя в свой Яндекс:
   https://oauth.yandex.ru → «Создать приложение». Название любое («Магнат
   копии»), платформа — «Веб-сервисы», Redirect URI — кнопка «Подставить
   URL для разработки». В «Доступ к данным» найти «Яндекс Диск REST API» и
   отметить только **«Доступ к папке приложения на Диске»**. Создать и
   скопировать **ClientID**. Открыть ссылку
   `https://oauth.yandex.ru/authorize?response_type=token&client_id=<ClientID>`,
   нажать «Разрешить» — на странице появится токен (строка вида `y0_…`).
   Токен живёт около года; истёк — `magnat status` покажет ❌, тогда снова
   этот шаг и `magnat backup-setup`.
2. **Фраза-ключ.** Придумать (не короче 12 знаков) и **записать на бумагу**:
   без неё копии не открыть — ни на новой машине, ни мне.
3. **Termius → сервер:** `magnat backup-setup` — спросит токен и дважды фразу
   (букв не видно). Успех: `КОПИЯ НА ДИСКЕ ЕСТЬ: magnat-NN.db.gz.enc (… КБ) в
   папке приложения на Яндекс Диске`. Токен и фраза лежат только в
   `/etc/magnat/` (root, 0600) — в чат их не присылать.
4. **`magnat status`** → `Яндекс Диск:    копия … ✅ (…, зашифрована; слотов 14)`.

Если `НЕ УШЛО: Диск не пустил…` — токен скопирован не целиком или истёк:
снова шаг 1. `…у токена нет доступа к папке приложения…` — при создании
приложения не отмечено право из шага 1. Прежние настройки при любом
«НЕ УШЛО» не трогаются.

**Открыть копию на новой машине:** скачать файл из папки приложения на Диске
(Яндекс Диск → «Приложения» → название приложения), затем
`openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -in magnat-NN.db.gz.enc -out magnat.db.gz`
и ввести фразу; внутри — gzip с базой SQLite. Восстановление одной командой
(`magnat restore`) — следующим шагом.

### Запросы людей о своих данных

Человек пишет на адрес поддержки — отвечаем командами на сервере, адрес
берём из его письма:
- `magnat user show АДРЕС` — есть ли аккаунт, когда создан и заходил,
  устройства, число версий, место на сервере, заказы (дата, тариф, сумма,
  статус, номер) и срок доступа (самого адреса в выводе нет).
- `magnat user export АДРЕС` — письмо «Твои данные в Магнате» с вложением
  `magnat-<дата>.json` уходит **только на этот адрес**, не в чат.
- `magnat user delete АДРЕС` — показывает аккаунт, спрашивает «Напиши ДА»,
  стирает почту и записи сразу; из копий они уйдут сами в течение 30 дней,
  из слотов на Диске — за 14. В приложении то же самое есть кнопкой.
  Покупателя без аккаунта (оплатил, не входил) спросит другое: «Отвязать
  почту, Telegram и IP от заказов и снять срок доступа?» — суммы и номера
  заказов остаются для чеков, уже без адреса.

### Оплата Магната (Платега, 17.10.2026)

Разовая оплата доступа: месяц — 299 ₽ (30 дней), год — 1 490 ₽ (365 дней),
без автосписаний. **Пока выключена:** посетители ничего нового не видят.
Включается одним коммитом по слову владельца и только вместе с открытием
входа по почте (в `CLAUDE.md` — раздел «Оформление и оплата»). Ключи и адрес
уведомлений можно поставить заранее — до включения по ним ничего не
происходит.

**После слияния этой версии — один раз `magnat upgrade`.** API обновится сам
вместе с сайтом, а скрипт сервера и служба — нет: только `upgrade` ставит
команды ниже, пустой `/etc/magnat/platega.env` и службу с
`LoadCredential=platega` — без неё API ключей не видит. В конце —
`VSE-GOTOVO`.

1. **Ключи** — в кабинете Платеги, мерчант `magnat-planer.ru`: ID мерчанта
   (MerchantId) и секретный ключ API. Termius → сервер:
   ```
   magnat platega
   ```
   Спросит ID и секрет (букв секрета не видно — так и надо; **секрет в чат
   не присылать**). Успех: `КЛЮЧИ ПРИНЯТЫ: записаны в /etc/magnat/platega.env
   (0600), API их видит.`
2. **Адрес уведомлений.** `magnat platega` печатает его следом — вписать в
   кабинете Платеги как адрес для уведомлений об оплате (Callback URL):
   ```
   https://magnat-planer.ru/api/platega/callback
   ```
   Без него оплата всё равно подтвердится (сервер сам спрашивает Платегу о
   каждом счёте), но медленнее, а возврат денег банком будет виден только
   при ежесуточной сверке — и только для оплат моложе 120 дней.
3. **`magnat status`** — новая строка, её и присылать:
   ```
   Платега:        ключи заданы · оплата выключена · ждут оплаты 0 · оплат за месяц 0 на 0 ₽ · последнее уведомление не было
   ```

`magnat platega off` — стереть ключи: новые счета не создаются, страница
оформления скажет «оплата не подключена», оплаченные сроки не тронуты.

**Если в строке «Платега:»:**
- **`⚠ счета не создаются: N за сутки → проверь ключи: magnat platega`** —
  Платега отказывает в создании счёта (чаще всего — неверный ID или секрет,
  либо мерчант ещё не активен), покупатель видит «Платёжный сервис не
  ответил» и уходит ни с чем. Скопировать ключи из кабинета заново →
  `magnat platega` → оформить месяц самому на сайте: открылась страница
  Платеги — ключи верные, платить не обязательно (без заказа ключи у Платеги
  не проверить). Счётчик — за сутки: ⚠ уйдёт сам, когда старые отказы станут
  старше суток. Не помогло — прислать вывод `magnat status` и `journalctl -u magnat-api -n
  30` (там `platega create <причина>`, ключей нет).
- **`⚠ ключи записаны, но API их не видит → magnat upgrade`** — служба
  поставлена до оплаты: `magnat upgrade`, потом `magnat status`.
- **`ключи не заданы → magnat platega`** — шаг 1.

**Команды для оплат** (каждая — одна строка в Termius):
- `magnat grant АДРЕС ДНЕЙ` — выдать доступ вручную: соглашение обещает
  «оплата прошла, а доступа нет 15 минут — включим вручную». Заказ на 0 ₽,
  дни прибавляются к остатку, отнять нельзя. Успех: `ДОСТУП ВЫДАН: … — до
  ДД.ММ.ГГГГ`; пусть войдёт в приложении по этой почте.
- `magnat orders [ГГГГ-ММ]` — оплаты месяца (по UTC) для чеков в «Мой
  налог»: дата, сумма, тариф, номер заказа, адрес маской, в конце итог.
  Возвраты (свой и банком) помечены «возврат — чек аннулировать» и в итог не
  входят. `magnat orders ГГГГ-ММ полностью` — с полными адресами, чтобы
  отправить чек покупателю; первая строка — `⚠ здесь полные адреса — в чат
  не присылать`.
- `magnat refund НОМЕР_ЗАКАЗА` — когда деньги уже вернул в кабинете Платеги
  (соглашение, раздел 5). Спросит «Напиши ДА», пометит заказ «возвращён»,
  срок доступа уменьшит на остаток этого заказа (дни других оплат
  остаются): `ВОЗВРАТ ЗАПИСАН: заказ N — возвращён, доступ теперь до …` или
  `…доступа у покупателя больше нет.` Затем аннулировать чек в «Мой налог».
  Номер — в `magnat orders` или `magnat user show`; срок по Москве, как в
  письмах, — тоже там. Повтор, неоплаченный или несуществующий заказ —
  `НЕ ЗАПИСАНО: …`, ничего не меняется.

**Письма-тревоги на адрес поддержки** (тема «Магнат: …», нужна настроенная
почта):
- «банк вернул деньги по заказу N…» — chargeback: доступ уже уменьшен сам,
  чек по заказу — аннулировать;
- «оплачен заказ N без почты…» — почта у заказа стёрта (аккаунт удалён,
  пока счёт ждал, или счёт оплачен позже 30 дней): выдать `magnat grant` по
  его письму в поддержку или вернуть деньги;
- «оплачен платёж …, которого нет в базе…» — база восстановлена из копии
  старше оплаты: найти платёж в кабинете Платеги, выдать `magnat grant`;
- «Платега прислала «оплачено» по заказу N, но за сутки не подтвердила…» —
  сверить в кабинете Платеги: оплачено, а доступа нет (`magnat user show`) —
  `magnat grant`.

### Оплата сервера

`magnat paid-until ДД.ММ.ГГГГ` — до какого числа оплачена машина RUVDS.
`magnat status` покажет `Оплата сервера: до … (осталось N дней) ✅`, за 5 дней
— `⚠`, и ночью придёт письмо «Магнат: Сервер оплачен до … — осталось N дней,
продли на RUVDS» на адрес поддержки (раз в сутки, пока не продлено или дата
не записана заново). Автопродление в RUVDS это не заменяет — только напоминает.

## VPN не задевается — проверено 02.10.2026

Владелец: «Впн там не наделай фигни. Не перепутай. Не сломай». Что сверено:

- **Ни один клиент VPN через эту машину не ходит.** Хост «Обход глушилок»
  выключен в панели 29.09 скриптом, который перечитывает панель после записи:

- **Сторож серверов VPN не поднимет тревогу:** он проверяет только то, что
  реально уходит клиентам в подписке, а этой машины там нет. Досмотр
  `checkup.sh` (шаг 15) спрашивает лишь, отвечает ли 443 из России, — Caddy
  отвечает.
- **DNS не перепутать:** домен VPN `genafast.xyz` живёт в Cloudflare, домен
  Магната — в REG.RU. Правка в REG.RU VPN не касается.
- 🔴 **Замок «не тот сервер»** — первое, что делает `install.sh`, до любого
  изменения. Следы VPN (`/opt/genavpn-repo`, `/opt/remnanode`,
  `/opt/remnawave`, боты, docker, xray) — стоп. Адрес машины не
  `193.108.113.70` — стоп. Вставленная по ошибке на сервер VPN, команда
  только скачает папку `/root/magnat-setup` и остановится. Сторож —
  `tests/06-server.js`, блок 1б; без замка он красный.
- Цена решения одна и известна: вернуть «обход глушилок» на этой машине
  нельзя, только на новой.

🔴 **Найдено после первой установки (02.10, 15:00):** установка сказала
«пересылка снята, правил убрано: 0», а порт 443 из Москвы отвечал за 50 мс
вместо 3 — то есть всё ещё уходил в Амстердам. Причина: 22.09 пересылку
включили руками, без метки `genavpn-relay`, а установка и `magnat status`
искали только по метке. Пять правил (DNAT 443 и 20443, MASQUERADE, два
ACCEPT в FORWARD) плюс их копия в `/etc/iptables/rules.v4`. Мерило, которое
это поймало, — время соединения по портам снаружи (`check-outside.py
--порт`), а не наш же вывод.
Теперь пересылка ищется по смыслу (на машине без docker любая DNAT/
MASQUERADE и ACCEPT прямо в FORWARD — её), цепочки ufw не трогаются.
Перед снятием — минута счёта новых соединений через пересылку: больше 30 —
стоп, ничего не тронуто (живой клиент VPN даёт десятки, сканеры — единицы).
Копия правил откладывается в `rules.v4.relay-old`, а не удаляется.
Сторожа — `tests/06-server.js`, блок 1в: разбор на точном выводе с сервера
и `tests/relay-netns.sh` — настоящий iptables в двух изолированных сетях
(живые соединения → стоп; тишина → сняты ровно пять, ufw цел, 443 отвечает
сам сервер). Три поломки (по метке, без счёта, шире чем надо) — красные.

**Найдено вторым запуском (02.10, 15:30):** установка упала на шаге 2 —
«Could not get lock /var/lib/dpkg/lock-frontend»: на свежей машине apt
держали автообновления. Вреда не было (всё стояло с первого запуска).
